# 灵矽语音对讲总体设计

状态：产品与技术总体方案。第一阶段的具体交互、报文和资源限制见[第一版设计](intercom-v1.md)。

## 1. 产品定位

灵矽对讲面向车队、调度和临时协作场景，也允许非司机用户使用。用户可用设备收听和发送同组语音；后续可通过语音加入或切换房间。linxd 保持语音助手与 OTA 的职责，对讲音频由独立服务转发。

典型过程：管理员创建“城东车队”房间并邀请成员，司机的设备绑定到其账号；司机说“加入城东车队”，linxd 理解指令并调用设备本地 MCP 工具；设备向对讲服务申请加入，成功后显示当前房间；司机在屏幕上录制并发送语音，房间内其他在线设备播放。

产品先做录完再发的语音消息式对讲。验证该体验后，再评估按住即实时传声。两种模式的延迟、发言权和缓存策略不同，不在第一阶段混用。

## 2. 分阶段范围

| 阶段 | 用户可见能力 | 技术重点 |
| --- | --- | --- |
| 第一阶段：链路验证 | 配网页面配置本机 ID 与 `ws://` 地址；触屏点击录音、再次点击发送；所有在线设备处于同一个固定广播域。 | 本机 PSRAM 暂存 Opus，点击发送后经独立 WebSocket 上传；单实例服务转发，接收端播放。 |
| 第二阶段：房间 | 创建、邀请、加入、退出和切换房间；设备一次只在一个活动房间收发。 | 房间与成员数据、设备绑定、权限校验、房间内路由；设备本地 MCP `join_room`、`switch_room` 等工具。 |
| 第三阶段：车队运营 | 常用房间、调度广播、临时任务房间、成员管理和更可靠的送达状态。 | 管理后台、审计、监控、跨实例路由；按使用情况评估实时对讲与离线语音。 |

阶段边界以[第一版设计](intercom-v1.md)为准：第一阶段没有目标 ID 字段、可选房间、语音切群、离线补播或正式业务录音管理。服务端默认可保存本地调试 WAV，并可通过参数关闭；后续能力不能反向成为第一阶段的前置条件。

## 3. 系统职责

```text
                          语音指令 / MCP 调用
设备上的小智助手 <--------------------------------> linxd
       |                                        （助手与 OTA）
       | 本地工具调用
       v
设备对讲管理模块 <---- 配置、房间状态 ----> 对讲控制接口
       |                                      |
       +---- Opus / WebSocket --------------> 对讲转发服务
                                              |
                                              +---- 其他在线设备

管理员或成员 Web/手机端 <---- 房间与成员管理 ----> 对讲控制接口
```

| 部分 | 负责 | 不负责 |
| --- | --- | --- |
| linxd | 语音识别、意图理解、回复播报、调用设备 MCP；沿用现有 OTA 接入。 | 转发或保存对讲 Opus 包。 |
| 设备本地 MCP | 暴露可执行的对讲命令，返回明确的成功、失败或待确认结果。 | 独立决定房间权限或代替媒体传输。 |
| 设备对讲管理模块 | 连接服务、管理当前房间和音频互斥、录制及播放、UI 状态。 | 直接改写现有助手的传输协议。 |
| 对讲控制接口 | 后续管理房间、成员、设备绑定、邀请和权限；给设备返回稳定房间 ID。 | Opus 编解码。 |
| 对讲转发服务 | 维护在线连接、校验消息、控制并发、转发 Opus；调试时可保存本地 WAV。 | ASR、TTS、OTA 或正式业务录音管理。 |

第一阶段可以只部署一个转发进程，不实现独立控制接口。房间上线时，控制接口和转发服务可先在同一进程内实现，但数据控制与音频转发职责应清晰分开。

## 4. 设备与用户标识

设备原有 `board.uuid` 用于固件既有能力；对讲“本机 ID”单独保存在 NVS，第一阶段由用户在现有 Wi-Fi 配网页面的“高级设置”填写。这个 ID 用于在线连接路由，不是永久身份凭证，也不是房间 ID。

第二阶段增加账号 ID、设备 ID 和房间 ID。账号拥有或管理设备，设备绑定账号，房间成员资格授予账号或组织，设备代表已绑定账号发言。房间名称可修改且可能重名，实际加入、切换和转发均使用不可变房间 ID。一台设备同一时刻只选择一个活动房间；退出或切换完成前不向新房间发送音频。

第一阶段采用明文 `ws://`，仅用于可信内网实验。身份认证、设备绑定校验和传输保护是进入公网或正式车队使用前的独立交付项；仅凭自报本机 ID 不能证明身份。未来的媒体传输和地址格式应在明确部署范围后决定，不能把第一阶段明文配置当作正式环境安全方案。

## 5. 建群与切群产品逻辑

### 建群入口

第二阶段由 Web 或手机端承担建群和管理，设备侧不承担复杂表单。管理员填写房间名称、所属组织、成员范围和邀请权限；成员可通过二维码、邀请链接或一次性邀请码加入，也可由管理员批量分配车队设备。邀请应有有效期和撤销能力。设备绑定与成员加入必须有可查结果，避免只凭语音说出房间名称就进入他人房间。

默认可设置“常用房间”。设备联网后恢复上次活动房间；若已失去权限，则退回无房间状态并提示。临时房间可随任务结束关闭；房间关闭或成员被移除后，服务端立即停止向相关设备转发语音。

### 语音操作

用户说“加入城东车队”或“切到调度群”时，linxd 调用设备本地 MCP。工具先向对讲服务查询当前账号可加入的房间：唯一匹配且有权限时申请切换；多个同名匹配时返回候选项让助手追问；找不到或无权限时返回明确原因。只有服务端确认成功，设备才更新当前房间，并让助手播报结果。

建议的 MCP 语义为 `list_rooms`、`get_current_room`、`join_room`、`leave_room`、`switch_room`。工具参数优先使用稳定房间 ID；自然语言名称只用于查找。网络请求应异步执行，MCP 和网络回调不能阻塞应用主循环或音频任务。切群时若正在录制、发送或播放，先结束当前会话或返回“稍后重试”，不能让一段语音跨两个房间。

## 6. 音频与消息路径

第一阶段遵循[第一版设计](intercom-v1.md)：设备触屏录音，Opus 帧保留在本地 PSRAM；点击发送后经独立 WebSocket 逐帧上传。服务端只转发给其他在线设备，不补播；默认保存本地调试 WAV，可关闭。接收端按顺序播放，同一广播域同时只允许一段语音转发。音频参数、帧上限和控制帧定义以第一版设计为准。

第二阶段把转发范围从全体在线设备改为当前房间内有收听权限的设备。服务端依据已确认的成员关系和活动房间路由，不信任客户端在音频帧中声明的目的房间。每段语音的开始消息携带房间 ID 和消息 ID；服务端在开始时固定该消息所属房间，切群不能改变已经开始的消息。发言权从全局互斥改为按房间互斥，避免不同房间互相阻塞。

继续沿用录完再发时，可按播放速度上传，降低接收端队列压力。若改为实时对讲，需要另行定义按住讲话、发言权租约、端到端时延目标、抖动缓冲和丢包处理。服务端缓存始终有上限；离线留言需另行定义保存期限、容量和清理规则。

## 7. 设备音频协调

设备的麦克风、Opus 编码器、解码器和扬声器与助手共用硬件。应用层统一协调音频所有权：录音或播放时，助手不再开启另一条采集或播放流；设备忙时拒绝收到的语音，避免混音或无限等待。UI、MCP 和 WebSocket 回调把请求投递给应用任务，主设备状态仍通过 `Application::SetDeviceState()` 管理。

目标板触摸已接入 LVGL，屏幕可提供“录音 / 发送 / 取消”；BOOT 键保留助手功能。其他板型可按能力提供触屏、物理 PTT 或仅接收，不要求核心对讲模块依赖具体板类。录制缓冲必须显式限制时长和 PSRAM 用量，不能假定标称 8 MB 全部可用。

## 8. 运维与验证

转发服务至少记录连接数、重复 ID、录音开始/结束、转发接收数、忙碌拒绝、慢连接丢弃、异常断线和帧数超限。日志只记录必要标识和错误，不记录 Opus 内容。设备屏幕呈现连接、录制、发送和播放状态，后续呈现活动房间。固件和服务端以版本字段协商消息格式；版本不兼容时明确拒绝并提示升级，不能静默错误播放。

第一阶段通过至少两台实机验证触摸、录音、广播、播放、断线重连和内存峰值。第二阶段增加重名房间、无权限、邀请过期、切群时并发录音、成员移除及跨房间隔离测试。每个阶段分别验证编译、服务端协议和真实硬件；编译成功不等于麦克风、扬声器或触摸链路已验证。
